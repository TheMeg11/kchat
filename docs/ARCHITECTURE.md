# Architecture — 2026-11-28

One Python process, one persistent PostgreSQL database. SQLite is for isolated development/tests only. No Redis, extra worker service or distributed scheduler is required or supported.

- **Ingress:** authenticated Telegram webhook (secret header + path), secret-path Bale endpoint and platform polling adapters feed `app/inbox.py`. Receipts persist before acknowledgement, deduplicate on platform/update ID, lease/retry with backoff, and dead-letter after a finite attempt budget. Two ordinary actor partitions by default plus a dedicated checkout lane. Completed payloads are cleared and receipts purged after 48 hours. Changing partition count with pending rows requires draining first.
- **Adapters:** `app/platform.py` wraps API differences, timeouts, bounded retries, per-chat locks and global/per-chat throttling. Telegram uses XTR and automatic refunds; Bale uses IRR/provider token and manual refunds. Bale runs polling. No external-send exactly-once guarantee.
- **Matching:** `service.py` reads bounded FIFO candidates, batches exclusion data and locks wallets/chats in short transactions. PostgreSQL advisory lock `71389202` serializes match cycles and a trigger guards against a user appearing in either position of two active chats. Network delivery is outside the match transaction, with compensation for failed connection notices. The **existing age policy is unchanged**; no separate age-pool guarantee.
- **Wallet/orders:** guarded SQL balance changes and unique idempotency ledger keys. Immutable server-side invoice orders bind amount/currency/payer/recipient. Payment settlement locks the order. Refunds reserve recipient coins before gateway calls; ambiguous responses stay pending for reconciliation.
- **Config/moderation:** local TTL caches with commit/rollback invalidation hooks, SQL parameter binding, normalized moderation dictionary/allowlist. Cross-process cache invalidation is not implemented.
- **Privacy:** retention jobs remove expired chat data. Account deletion removes conversation/social/support data and scrubs the profile, preserving a pseudonymized financial row. Off-platform backup deletion and statutory financial retention are operator responsibilities.
- **Backup:** repeatable-read batched export, bounded spool/gzip, AES-GCM/scrypt, 18 MiB Telegram parts, separate export/delivery state. Restore is owner-only, bounded, session-upload-bound on the web, password+phrase confirmed without TOTP. Shared SQL backup/restore advisory lock `71389201`, local mutation/worker gate, emergency encrypted snapshot, transactional replacement/consistency checks. See backup guide for prerequisites and limits.
- **Chat controls:** chat-ID-bound callbacks validated against the current active chat, with persisted control metadata and best-effort keyboard retirement. In-memory maps are bounded; stale presses must not operate on a newer chat. Relayed content carries no new chat controls.
- **Broadcasts:** SQL audience count, keyset batches of 25 and committed cursor/counters, no whole-audience materialization on creation. Campaigns resume from SQL `sending` state after restart. Hard crashes may repeat a batch; failed sends are counted rather than guaranteed eventually delivered. Audience is evaluated per batch.
- **Web panel:** FastAPI `/api/admin/v1`, RBAC, audited bounded/lazy history, 30-day default revocable sessions, session-bound refreshable CSRF, Argon2id and password rotation. No TOTP. User search filters/counts/pages server-side. Frontend is an editable recovered React bundle with a reproducible esbuild pipeline, not the missing original JSX tree.
- **Scheduler/monitoring:** independently caught/time-budgeted jobs prevent one failure from skipping all later jobs (one slow job can still delay the loop). Broadcast work runs independently. Local samples are bounded to 288 points; process/cgroup measurements are not Railway bills or historical uptime. Unknown fields remain null.
- **Migrations:** legacy additive bootstrapping followed by versioned forward SQL migrations under PostgreSQL advisory DDL lock `71389203`. Large index changes require a maintenance window; no automatic downgrade path.

Distributed restore, cache invalidation, actor ordering and broadcast leasing would be required before adding multiple processes or replicas. Do not infer distributed safety merely from use of PostgreSQL locks.
